# Архитектура

## Структура

Исходный код находится в `src/main/java/dev/codingagent`. Пакеты объединяют данные
и операции одной части приложения; тесты повторяют ту же структуру.

| Пакет | Назначение и основные классы |
|---|---|
| `cli` | Разбор команд, сборка приложения и вывод: `AgentCli`, `CliSession`, команды |
| `agent` | Цикл модели и исполнение инструментов: `Agent`, `ToolExecutor`, `ExecutionHook` |
| `model` | HTTP- и сценарный клиенты, сообщения, инструкции: `ModelClient`, `Conversation` |
| `run` | Запуск, статусы и решения: `RunState`, `RunService`, `RunRules` |
| `run/recovery` | Разрешение неопределённых попыток: `RecoveryService` |
| `plan` | Структура и утверждение плана: `WorkPlan`, `PlanService` |
| `task` | Зависимости, состояния и подтверждения: `TaskService`, `TaskEvidenceCollector` |
| `budget` | Лимиты, расход и резервирование вывода: `BudgetService`, `BudgetRules` |
| `journal` | Учёт изменений: `JournalService`, `JournalRules` |
| `journal/snapshot` | Снимки путей и содержимого: `WorkspaceTree`, `TreeSnapshot`, `PathImage` |
| `journal/diff` | Сравнение снимков и печать diff |
| `journal/rollback` | Проверка конфликтов и восстановление: `RollbackService`, `RollbackFiles` |
| `tools` | Интерфейс, схемы, проверка аргументов и ограничение результатов: `ToolRegistry` |
| `tools/files`, `tools/bash` | Файловые инструменты и выполнение процесса Bash |
| `tools/execution` | Вызовы и попытки: `ToolCallService`, `ToolCall`, `ToolAttempt` |
| `storage` | SQLite и транзакции: `StateStore`, `StatePaths` |
| `config`, `json` | Конфигурация и общие операции с JSON |

Точка входа — [Main.java](../src/main/java/dev/codingagent/Main.java).
Основной цикл — [Agent.java](../src/main/java/dev/codingagent/agent/Agent.java).

## Цикл и сохранение

1. CLI открывает хранилище и создаёт либо загружает запуск по `run_id`.
2. При исполнении `TaskService` выбирает задачу с завершёнными зависимостями.
3. Сначала выполняются уже сохранённые ожидающие вызовы. Если их нет, runtime
   списывает запрос из бюджета и передаёт модели историю и схемы инструментов.
4. Ответ assistant и определения всех его вызовов сохраняются одной транзакцией.
   Реестр определяет свойства инструмента, а runtime назначает `task_id`.
5. До первого инструмента проверяется и резервируется бюджет всей пачки.
6. Перед реальным действием сохраняется попытка `STARTED`. Для записи и Bash
   также проверяется дерево проекта и сохраняется снимок до действия.
7. Инструмент исполняется вне SQL-транзакции. Затем одной транзакцией сохраняются
   результат, сообщение `role: tool`, расход вывода и изменения файлов.
8. Ошибка инструмента возвращается модели с исходным `tool_call_id`.
   Текстовый ответ проверяется как предложение завершить текущую задачу.
   После всех задач запуск становится `COMPLETED`.

При исполнении плана модель получает определения инструментов текущего шага;
после его подтверждения runtime выбирает следующий шаг и обновляет набор.
При двух одинаковых неуспешных вызовах подряд в историю добавляется просьба
разобрать причину ошибки перед следующей попыткой. Лимиты бюджета продолжают действовать.

`ExecutionHook` расположен между реальным действием и записью результата.
Через него тесты и `--crash-after-call` воспроизводят сбой в этом промежутке.
Неизвестный инструмент, неверный JSON, тип или лишнее поле аргументов дают
результат с `success=false`, позволяя модели исправить следующий запрос.

Повторный ID с тем же определением использует сохранённый результат без повторного
действия. При новом ответе assistant для него добавляется соответствующий ответ
`role: tool`. Другое имя или аргументы при том же ID — ошибка протокола.
Сравнение JSON не зависит от порядка ключей объекта и формы записи чисел.

## Хранилище и состояния

SQLite содержит одну прикладную таблицу `runs(run_id, state_json)`. `RunState`
хранит цель, полную историю, вызовы и попытки, решения пользователя, план, задачи,
бюджет, журнал и состояние отката. Изменения выполняются через `StateStore.update`
в коротких транзакциях `IMMEDIATE`; исключение откатывает весь update.
Используются `synchronous=FULL` и ожидание блокировки до 5 секунд.

Сообщения и результаты хранятся JSON-объектами с сохранением дополнительных полей
провайдера. Поле `content` сообщения `role: tool` содержит строку JSON с результатом,
как требует формат Chat Completions API.
При отправке истории API-клиент исключает `reasoning`, `reasoning_content` и
`thinking` из копий сообщений assistant. Полные исходные ответы остаются в SQLite;
повторно отправляются текст ответа, вызовы инструментов и остальные поля провайдера.
Загруженные объекты отделены от базы: их изменение само по себе ничего не сохраняет.
Файл базы называется `runs.sqlite`. Каталог состояния и workspace должны быть
отдельными, невложенными каталогами.

| Статус запуска | Значение |
|---|---|
| `PLANNING` | Изучение проекта и подготовка плана |
| `AWAITING_APPROVAL` | Ожидание решения пользователя |
| `EXECUTING` | Исполнение задач |
| `RECOVERY_REQUIRED` | Есть неопределённые попытки |
| `COMPLETED`, `FAILED`, `ROLLED_BACK` | Завершение, ошибка или выполненный откат |

Фаза планирования или исполнения сохраняется отдельно и восстанавливается после
разрешения сбоя. Формат состояния — версия 2. Старые, неизвестные или неполные
снимки отвергаются без изменения сохранённых данных; автоматической миграции нет.

## Восстановление

Сохранённый результат не исполняется заново. Вызов без начатой попытки остаётся
ожидающим. Попытка `STARTED` без результата становится `UNCERTAIN`:
файловая система и SQLite не образуют общую транзакцию, поэтому результат действия
нельзя достоверно восстановить только по его аргументам.

Пользователь выбирает `retry`, `skip` или `fail`. Безопасно повторяемыми считаются
только `list_files` и `read_file`: они не меняют проект. `retry` создаёт новую попытку
того же вызова, сохраняя прежнюю. Запись и произвольный Bash повторять запрещено.
`skip` сохраняет ошибку инструмента, `fail` дополнительно завершает запуск.
Решение и его применение сохраняются атомарно.

Для неопределённого побочного действия сначала сохраняется наблюдаемый снимок
и его хеш `observation`. Пользователь явно включает обнаруженные изменения
в журнал запуска либо исключает их как внешние. Перед применением решения дерево
снова сравнивается с просмотренным. При несовпадении нужен новый просмотр.
Исключение не снимает защиту с ранее изменённых запуском путей: посторонняя версия
такого файла вызывает конфликт при следующем изменении или откате.

## План и подтверждения задач

До утверждения разрешены только инструменты чтения; весь Bash запрещён независимо
от аргументов и флагов в ответе модели. Сначала модель изучает проект инструментами.
После текстового итога отдельный запрос без инструментов формирует план через
`response_format: json_schema`; схема находится в `src/main/resources/plan-schema.json`.
Ожидание структурированного ответа сохраняется в `planDraftRequested`, поэтому
после ошибки API `resume` продолжает этот этап без повторного изучения проекта.
Разделение позволяет не смешивать tool calling и ограничение формата ответа.
`WorkPlan` дополнительно проверяет граф и условия подтверждения; неверный план
возвращается модели для исправления. Готовый корректный JSON, в том числе из
сценарного клиента, принимается сразу. При утверждении сохраняются решение,
явная инструкция о завершении Plan Mode и переход в исполнение;
само исполнение начинается при `resume`. Отклонение завершает запуск с ошибкой.

Шаг плана содержит ID, описание, инструменты, зависимости и `expected_result`.
Проверяются уникальность ID, существование зависимостей и отсутствие циклов.
Задачи исполняются последовательно; состояния: `PENDING`, `RUNNING`, `COMPLETED`,
`FAILED`. Вызовы исполнения относятся к текущей задаче, вызовы планирования — без `task_id`.

Проверка результата использует сохранённые успешные, необрезанные ответы инструментов
этой задачи, при необходимости — конкретный путь и фрагмент содержимого.
В схеме для модели файловые проверки задаются инструментом и путём, а Bash —
именем инструмента. Дополнительное условие `contains` поддерживается runtime
и используется в подготовленных JSON-сценариях.
Для Bash дополнительно нужны нулевой код завершения и отсутствие таймаута.
Проверка должна следовать за последней записью или Bash; повтор старого результата
из кеша не делает её свежей. Подтверждения содержат фактический результат и номер
попытки, сохраняясь атомарно с завершением задачи. Обычный `run` создаёт одну
задачу `main` с обязательной успешной проверкой Bash.

## Учёт бюджета

Бюджет действует на весь `run_id`, включая планирование, исполнение и восстановление.
Запрос модели списывается до обращения к API; ошибка не возвращает расход.
Пачка инструментов допускается целиком: недостаток любого ресурса останавливает её
до исполнения и без частичного списания.

Для каждого результата заранее резервируется объём. Инструмент получает доступный
предел, а окончательный JSON с `success`, `output` и `truncated` ограничивается
по размеру UTF-8. При успешном сохранении неиспользованный резерв освобождается.
При сбое резерв считается потраченным. Явная новая попытка требует нового бюджета.
Кешированный ответ расходует вызов и байты результата, но не побочное действие.

## Журнал и откат

Снимок охватывает все обычные файлы и каталоги, включая скрытые и генерируемые.
Содержимое хранится точными байтами в Base64 с SHA-256. Перед записью и Bash всё
дерево сверяется с последним ожидаемым снимком. После действия сохраняется
фактическая разница, даже если инструмент вернул ошибку или Bash завершился ненулевым кодом.
Для каждого затронутого пути остаются первое состояние до изменения и последнее после.

Текстовый diff показывает содержимое целиком как удалённые и добавленные строки,
а не минимальный патч. Для бинарных файлов и каталогов выводится сводка.
Откат использует точные исходные байты, включая исходные переводы строк.

Перед откатом проверяются все затронутые пути, их типы, хеши и безопасность итогового
дерева. Посторонний файл внутри созданного агентом каталога также вызывает конфликт.
Если хотя бы одна проверка не пройдена, запись не начинается. Остальные пути проекта
сохраняются. Неопределённые вызовы должны быть разрешены заранее.

До файловых операций сохраняется намерение отката. Затем удаляются затронутые файлы,
пустые каталоги — от глубоких к верхним, создаются исходные каталоги и записываются
исходные файлы. Рекурсивное удаление не используется. Повтор прерванного отката
принимает только известные исходные, итоговые и предусмотренные промежуточные
состояния; неизвестный хеш останавливает продолжение. Уже восстановленные пути
пропускаются. После проверки результата сохраняется `ROLLED_BACK`.
Повтор завершённого отката файлы не перезаписывает.

Пределы снимков, инструментов и команды CLI приведены в [README.md](../README.md).
